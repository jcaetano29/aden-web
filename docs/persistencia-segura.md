# Persistencia segura

Las lecturas de personajes, cuentas y guilds distinguen dos resultados: una consulta exitosa sin fila devuelve `null`; un error de Supabase o de transporte rechaza la promesa. Las escrituras y consultas de ranking también rechazan cuando Supabase no confirma la operación. El error conserva la causa original para el diagnóstico del servidor, pero los clientes reciben un mensaje general en español sin SQL, nombres de tablas, hosts ni detalles del proveedor. Los rankings conservan el último snapshot válido si falla su actualización.

El nombre autenticado usa `trim` y distingue mayúsculas como antes. Ese nombre es la clave de cuenta, personaje, reserva y guardado; `onJoin` usa `auth.name`, sin volver a interpretar el nombre enviado. La reserva se adquiere sin esperar operaciones de almacenamiento. Un segundo acceso o creación para el mismo nombre se rechaza con un mensaje de sesión activa/guardado en curso, incluso entre salas de un mismo proceso; nunca expulsa al primer cliente. Otros nombres pueden seguir accediendo y guardándose.

El acceso verifica la cuenta y contraseña, reintenta el snapshot pendiente si existe y luego carga el personaje y su guild antes de crear estado jugable. Una lectura o escritura fallida rechaza el acceso, sin crear un personaje de nivel 1 ni una guild vacía. Una guild inexistente después de una consulta exitosa conserva la reconstrucción compatible basada en el personaje.

`CharacterPersistenceCoordinator` mantiene una cola por nombre y un token de propiedad por conexión. `acquire` reserva sincrónicamente; `save` copia el snapshot y ordena la escritura después de las anteriores; `retry` confirma el pendiente usando el proveedor que recibió la escritura original; `release` espera las escrituras en curso y libera solamente el token correcto. La instancia compartida cubre todas las `GameRoom` del proceso. Un fallo no envenena la cola ni reemplaza el snapshot más reciente por uno antiguo. Inventario, equipo, achievements y learnedTomes son copias independientes.

Al salir, el jugador se retira inmediatamente de combate, grupos, chat y estado vivo. El snapshot final se encola detrás del autosave que ya haya empezado. La propiedad permanece retenida hasta que ese trabajo termina. Si falla, se registra el error y el último snapshot queda pendiente en memoria; no se informa guardado exitoso. El próximo acceso autenticado reintenta antes de leer. Si el reintento vuelve a fallar, rechaza el acceso por disponibilidad y mantiene el pendiente para otro intento. No hay bucles automáticos ni timers de reintento.

Un cierre de socket durante autenticación tiene limpieza propia: Colyseus puede omitir `onLeave` antes de insertar al cliente. La reserva no se libera hasta que la lectura o escritura de cuenta ya iniciada termina. La sala no instala un jugador después del cierre. `onDispose` también retira sesiones y espera operaciones en vuelo; los pendientes fallidos pertenecen al coordinador y sobreviven a la eliminación de la sala. Un callback o liberación de una sesión anterior no puede liberar la nueva.

Para recuperar un fallo transitorio, restaurar la disponibilidad del proveedor y volver a intentar el acceso con las mismas credenciales. Mientras una operación no termina, ese nombre permanece reservado: no se añade un timeout que permita adelantar una escritura posiblemente aún activa. Revisar los errores del servidor si el proveedor queda colgado.

La garantía alcanza un único proceso de servidor. Las reservas y pendientes viven en memoria: un reinicio o caída del proceso puede perderlos; varios procesos necesitan coordinación duradera en almacenamiento. El proveedor in-memory sigue siendo temporal y aislado por sala, como antes: no garantiza recuperar el personaje desde otra sala y no sustituye a Supabase. Las pruebas entre salas usan explícitamente un backend temporal compartido. No se modifican tablas, columnas, IDs, formatos guardados ni credenciales. Las escrituras de clanes quedan fuera de esta coordinación.

La verificación usa snapshots con promesas controladas, almacenamiento temporal y clientes Colyseus reales: orden de commits, progreso final, recuperación tras rechazo/dispose, acceso concurrente en una o dos salas, contraseña, identidad canónica y cierre durante autenticación. No requiere llamar a Supabase real.
